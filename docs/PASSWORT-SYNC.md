# Vault sync (passwords + passkeys) — concept only

Status: **concept. Nothing here is built or switched on** (31.10.2026, roadmap P1-3 note / r2416). Base document: Certus `docs/PASSWORT-SYNC.md` (03.10.2026, same principles for the browser password store). This file adds what changes for the system vault and for passkeys. The vault itself is `docs/vault/vaultd.md`.

## 1. Principle

- The vault works completely without an account. Sync is an extra, off by default, switched on in Settings with a plain-language consent.
- The server only ever sees ciphertext plus size, revision and time. Nothing in vaultd or the vault lib contains network code; the sync module is a separate client of the vault lib (`vault.merge`).

## 2. What exists on the server side (measured in Certus docs)

- The sync service (`store.fleitec.com/sync/`) stores one record set `tresor`: raw octets up to 8 MiB. It only checks the head (`CERTUSTRESOR` + version 1) and that the length fits (`tresorPlausibel`). It does not check the KDF.
- Consequence for v2: the plausibility check must also accept the `VAULT2` magic (server change, with a test instance first — never against the live system without the owner's agreement). Until then sync can carry a v1-wrapped sync container (see §3).

## 3. Keys

```
SK   32 random octets, created on the first device when sync is switched on, never sent.
Sync container = vault container v2 with ONE slot of kind "sync": VK wrapped under SK.
```

- The sync container is a *separate* vault file: records copied from the local vault (selected by the switches in §5), sealed under a fresh VK that only SK unlocks. The local main password and PIN never touch the server and may change freely without any upload.
- Recovery of SK: (a) a recovery phrase generated by the program (not user-chosen), protected with Argon2id (`std.crypto.argon2`), or (b) device pairing: an enrolled device wraps SK for the new device's X25519 public key (`std.crypto.x25519`; the "WRAP 2" idea of Certus `ckkeys.fi`). Pairing shows a short code on both screens and a QR; no secret in the QR.
- Device removal: new SK, re-upload; the removed device keeps what it already had.

## 4. Merge

- Record level, last writer wins by `(id, modified_ms)`; deletions are tombstones (kept 90 days); implemented once in `vault.merge`, with the property test (commutative, associative, idempotent) shared with Certus.
- Conflict on upload (`409`, stale base revision): download, merge locally, upload again with the new base. No dialog.
- Clock skew: `modified_ms` from a device clock more than 24 h in the future is clamped to "now" before comparing.
- Passkey specifics: the same `credential_id` with different key material is a conflict that must never auto-resolve silently — keep the older one as a `superseded` copy, mark both, and show it in Settings. Resident duplicates for the same `(rp_id, user_handle)`: the newer wins, the older is tombstoned (CTAP replacement rule).
- Unknown record types and unknown keys inside records are carried through unchanged, so an older device does not destroy fields written by a newer one.

## 5. Switches (all default off)

| Switch | Effect |
|---|---|
| Sync logins | login records go into the sync container |
| Sync passkeys | passkey records (with private keys) go into the sync container; sets BS=1 on them (`vaultd.md` §5) |
| Device-bound passkeys | credentials bound to a TPM never sync (not created in v1) |

"Off + delete" empties the server record set (tombstone upload, account stays).

## 6. What the server and a network attacker see

| Visible | Not visible |
|---|---|
| a record set exists, its size (padded to a multiple of 4 KiB), revision, time, account id, IP | number of entries, sites, user names, passwords, passkeys, SK, main password, PIN |

An attacker with only the server cannot open the container (256-bit random SK); the recovery phrase is the weak spot and is generated, long and Argon2id-protected. A stolen account password can download, not open, but could overwrite or delete (availability): server keeps the previous version for 30 days (draft, owner decides), clients notice a revision jump at the next sync and show it.

## 7. Threats specific to passkeys

| Threat | Handling |
|---|---|
| Passkeys copied to a weaker device | Pairing is a user action with UV on the enrolled device; the new device must itself have a verifier (PIN/password) before it accepts passkeys. |
| RP treats backup-eligible passkeys as lower assurance | BE/BS flags are reported honestly (BS only when a sync or sealed export copy exists). |
| Rollback of the sync container | Revision counter inside the authenticated header; devices refuse lower revisions than they have seen (warn, never silent). |
| Lost last device | Recovery phrase restores SK; without it the server copy is unreadable by design. |
