# X-Remote host as an XoffiOS service (design, 04.11.2026, r2820)

Status: design + host flags only. Nothing of the Osum side is built or tested yet.

## 1. Architecture (decided)
- Package `xremote` (Store/OTA, `/apps/xremote.prog/`): `freeviewer-host` (musl-dynamic, branch `osum-host-only` of the FreeViewer repo), `lib/ld-musl-x86_64.so.1`, `lib/libgcc_s.so.1`. Started through the explicit musl loader, so no `/lib/ld-musl` is needed (public image has none; the personal image has it with BBSH=1).
- Supervisor `/bin/xremoted` (own Firn code, root, ~200 lines, in the base image, nothing foreign): inittab line `xremote:grafik:respawn:/bin/xremoted`. Idle (2 s poll) when `/etc/xremote.conf` has `enabled=0` (default) or the package is absent. When enabled and a person is signed in: writes a random 8-char password to `/run/xremote.pw` (0600), spawns the host with `--relay --password-file --state-file /run/xremote.state --home /run/xremote --insecure-relay(only if relay is ws://)`, restarts it on exit, kills it on disable. No environment is needed: the Osum exec call has no envp, so the host takes flags (done in the FreeViewer branch, commit "host: flags ...").
- Settings UI without a new window: schema keys in `etc/settings.schema` (settingsd is root, `store <file> <field>`): `remote.enabled` bool critical -> `/etc/xremote.conf enabled`; read-only status keys `remote.id`, `remote.password`, `remote.status`, `remote.peer` -> `/run/xremote.state` (written by the host every 2 s, key=value). The switch is `critical`, so the bus always asks a human.
- Capture/input: the host already uses `osum_shot` (SH_ARM/SH_GRAB, per-head rects) and `osum_tipp` (strokes, wheel) and the system bus clipboard; the gate `tools/xremote/run.sh` proves this on stage 0 (26/0, 2 heads 34/0, XR_DESKTOP=1 28/0). Emergency stop: `input off`, Super+Esc.
- Consent: password mode only (visible in Settings). Ask mode (0x06) needs a confirm dialog and is not implemented in the headless host.

## 2. Login screen (threat model, NOT implemented)
Default and only supported mode: the host runs only while a person is signed in (supervisor checks for the `taskbar` process). Threats if the host ran at glogin: remote password guessing against an unlocked machine (relay ID is stable, 8 chars from a 32 alphabet), shoulder surfing of the password on a screen nobody owns, typing credentials through the relay operator path (relay sees only ciphertext, but a compromised viewer device gets the OS account password), no human present to consent. Needed before it can exist: a second explicit setting `remote.login_screen` (off, critical), a pre-shared long secret instead of the short password, rate limit + lockout in the host, a kernel permit refusing `osum_tipp` for anything but an authenticated viewer session, audit log. Roadmap item added.

## 3. Android FreeViewer compatibility
No Android FreeViewer source or build exists on this server (searched /root/projects/freeviewer, freeviewer-flei, firnchat-android, /srv/jarvis-projects; the `flei-*.apk` files are a different app). Protocol of the host is `freeviewer-v1` (docs/freeviewer-protocol.md, FreeViewer 0.30.0, relay `/fv/ws`, E2E X25519+HKDF+AES-256-GCM, Argon2id proof). Provable now: the Rust viewer of the same 0.30.0 protocol (`freeviewer --connect`, `--inputtest`) against the Osum host (gate 26/34/28). NOT provable without a phone or the app build: the Android app's own protocol version string, its tile/H.264 caps, touch-to-mouse mapping, soft-keyboard key codes, background/network switching, and the relay FV_RELAY value it ships with.
